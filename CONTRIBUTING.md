# Contributing to Tacqor

Thank you for considering a contribution. This document explains how the project is organized, how to build and test it, what a good change looks like, and how changes are reviewed.

## 1. Ground rules

- **Programs that compile today must compile tomorrow.** Language changes are additive. A change that alters the meaning of an existing program needs a very strong reason and a major version.
- **Every backend must agree.** The VM, portable bytecode, embedded executables and native builds must produce byte-identical output for every program. A feature is not done until `tests/smoke.sh` passes through all four.
- **Every failure is a diagnostic.** No input — source, bytecode, network data — may crash the toolchain. New code paths that can fail must throw `Error` (compile time) or `std::runtime_error` (run time) with a message that names the problem.
- **Keep the language small.** A new feature should remove more complexity from user programs than it adds to the language. The whitepaper's design principles (`docs/WHITEPAPER.md` §2) are the test.

## 2. Getting set up

```sh
make                      # builds ./tacqor with the system C++17 compiler
make test                 # runs tests/smoke.sh against ./tacqor
```

Useful variants:

```sh
make CXXFLAGS="-O1 -g -fsanitize=address,undefined"      # sanitized build for debugging
make CXXFLAGS="-O3 -DTACQOR_NO_THREADED"               # the switch-dispatch VM that MSVC uses
TACQOR_HOME=$PWD ./tacqor run examples/primes.tq     # run with the in-tree standard library
```

Documentation tooling (needs `pandoc` and Python 3):

```sh
python3 -I tools/verify_docs.py . ./tacqor docs/COOKBOOK.md docs/FROM_PYTHON.md docs/FROM_RUST.md   # compiles/runs every snippet
python3 -I tools/build_html.py . docs/html                                                           # regenerates the HTML edition
```

`src/embedded_runtime.inc` is generated by `make` from `tacqor.hpp` and `values.hpp`; never edit it by hand, and commit the regenerated file whenever those headers change (the Windows build script does not regenerate it).

## 3. Where things are

| Area | File | Doc |
|---|---|---|
| Shared data model (types, ops, builtins enum, Program) | `src/tacqor.hpp` | `docs/ARCHITECTURE.md` §2 |
| Lexer, parser, type checker, code generator, optimizer | `src/compiler.cpp` | §3 |
| Runtime values, containers, collector, builtins, sockets | `src/values.hpp` | §4 |
| VM | `src/runtime.cpp` | §5 |
| Bytecode encode/decode/verify, embedded executables | `src/artifact.cpp` | `docs/BYTECODE.md` |
| Native backend (bytecode → C++) | `src/native.cpp` | `docs/ARCHITECTURE.md` §8 |
| CLI, REPL, packages, diagnostics | `src/main.cpp` | `docs/TOOLING.md` |
| Standard library | `std/*.tq` | `STDLIB.md` |
| Tests | `tests/` | `docs/ARCHITECTURE.md` §11 |
| Editor extension | `editor/` | `docs/TOOLING.md` §6 |

`docs/ARCHITECTURE.md` §12 has step-by-step recipes for the common changes: adding a builtin, adding an opcode, adding a type kind, adding a standard module.

## 4. Making a change

1. **Open an issue first** for anything beyond a bug fix or a documentation correction. Describe the problem, not just the solution; include a program that shows it.
2. **Branch** from `main`.
3. **Write the test before the fix.** Language features go into `tests/features_<version>.tq` with the expected output appended to the matching `.expected` file; CLI, error-message and tooling behaviour go into `tests/smoke.sh`; library functions get a `def test_*()` in `tests/unit_tests.tq`.
4. **Implement** following the recipes in `docs/ARCHITECTURE.md` §12. A new builtin or op has a checklist of places to touch; the `static_assert` in `values.hpp` catches a missing arity entry, and `tests/smoke.sh` has a check that every op has a name in `tacqor dump`.
5. **Run everything**: `make test`, then the sanitized build (`make CXXFLAGS="-O1 -g -fsanitize=address,undefined" && make test`), then `sh benchmarks/run.sh` if you touched the VM, the native backend or the runtime (performance regressions are bugs).
6. **Update the docs** in the same change: `LANGUAGE.md`/`STDLIB.md` for anything user-visible, `docs/SPECIFICATION.md` for semantics, `docs/BYTECODE.md` for opcodes, `docs/ERRORS.md` for new messages, `CHANGELOG.md` always.
7. **Open a pull request** with: what changed, why, how it was tested, and a before/after program when behaviour changed.

## 5. Code style

**C++**
- C++17, no exceptions for control flow except the `Error`/`ExitRequest` types already used; no RTTI-dependent code; no platform-specific code outside the clearly marked socket and process sections.
- Four-space indentation, braces on the same line, `snake_case` for functions and variables, `PascalCase` for types, `constexpr` over macros.
- Prefer `std::string_view`, `std::vector` and indices over raw pointers. Every container access on data that came from outside (bytecode, network, source) is bounds-checked.
- Comment *why*, not *what*. A comment that restates the next line is removed in review.
- Warnings are errors in spirit: the build must be clean with `-Wall -Wextra -Wpedantic`.

**Tacqor (standard library and tests)**
- Follow `docs/STYLE.md`. Library functions take the collection first (`lists.map(items, f)`), the same convention as the builtins, which makes `items.push(x)` and `lists.map(items, f)` read alike (method-call syntax resolves builtins and same-module functions; imported functions are always called qualified).
- Every public library function has a test in `tests/unit_tests.tq` and a row in `STDLIB.md`.

## 6. Commit messages

One change per commit. First line under 72 characters, imperative mood, prefixed by area: `compiler:`, `vm:`, `native:`, `runtime:`, `std:`, `cli:`, `docs:`, `tests:`. The body explains the why and names the issue.

```text
compiler: allow locals to shadow module names

A `let lists = ...` inside a function that imports std.lists failed with
"name is a module". Shadowing is harmless because module members are
always reached through the qualified form. Fixes #42.
```

## 7. Continuous integration

Every push and pull request runs `.github/workflows/ci.yml`: a GCC build with the full suite and every documentation snippet, a Clang build of the switch-dispatch variant with `-Werror`, the suite under AddressSanitizer and UndefinedBehaviorSanitizer, a macOS build with the suite, and an MSVC build with a smoke test on Windows (the macOS job is non-blocking because GitHub's hosted macOS runners are capacity-limited). A check that `src/embedded_runtime.inc` is up to date fails the build if the headers changed without regenerating it.

Pushing a tag `vX.Y.Z` runs `.github/workflows/release.yml`, which builds the static Linux binary, the macOS and Windows binaries, the standalone package and checksums, and attaches them to the release for that tag (creating the release if it does not exist). Changes under `docs/` on `main` redeploy the website through `.github/workflows/pages.yml`.

## 8. Review

A maintainer reviews every pull request for: correctness across all four backends, diagnostics for every new failure path, documentation, test coverage, and fit with the design principles. Reviews are about the code, not the author; comments are expected to be specific and actionable. Two approvals are needed for language changes, one for everything else.

## 9. Reporting bugs

Include the Tacqor version (`tacqor --version`), the platform, the smallest program that reproduces the problem, the exact command, and the full output. A crash (not a diagnostic) in any tool is always a bug worth reporting even without a minimal program. Security-relevant bugs go through `SECURITY.md`, not the public tracker.
